# platform-core 1.3.0: the app's own transaction, and mail through platform-outbound

Design note (P057, LV-25.2 and LV-24.3). No code. Everything here is **additive and off by default**: an app that changes nothing gets 1.2.0's behaviour.

**Built in P059 (1.3.0):** section 1 as written; section 2 step 1 only (token requests, and Teams and Slack, which the apps asked for), with one port
`transport.HttpTransport` for the three instead of `MailTransport`. SMTP, `mail.allowed-hosts` and `mail.smtp-proxy` are step 2 (1.4.0). Details in
`docs/design/case-fields.md` and `docs/design/notifications.md` ("Added in P059").

## 1. Field stores in the app's transaction (LV-25.2)

### 1.1 Today

Each call of `PostgresFieldStore` and `PostgresValueStore` takes a connection from its `DataSource`. A read runs on it as it is; a write sets auto-commit off, commits or
rolls back, and puts auto-commit back (`Sql.inTransaction`, and the store's own copy). So the app's row and the field values are two commits: a crash in between leaves one without the other.

| Call of `FieldValues` | Store calls | Transactions today |
|---|---|---|
| `claim` | `findByIdentity`, `find`, then `insert` or `replace` | one per call; up to 5 attempts |
| `update`, `rewrap` | `find`, `replace` | one per call; `update` up to 5 attempts |
| `erase` | `find`, `delete` | one per call; only through the erase log |
| `FieldDefinitions.change(list)`, `create` | `saveAll`, `create` | one |

What the stores rely on:

- **Optimistic version** (`where version = ?`, `VALUES_CHANGED_MEANWHILE`, then `FieldValues` reads again and retries).
- **`insert … on conflict do nothing`**, which waits for a concurrent writer of the same key, then **reads the other writer's row** in the same transaction. That read sees it only under READ COMMITTED.
- **Unique violation on `replace`** (SQL state 23505), turned into `VALUES_PRIMARY_TAKEN`. The failed statement **aborts a PostgreSQL transaction**; today the store rolls back its own, so nobody notices.

### 1.2 The choice: a connection handed over per call

| Way | Without Spring | With Spring | Changes existing behaviour |
|---|---|---|---|
| **A. `onConnection(Connection)`, as the identity stores have** | yes | yes (`DataSourceUtils.getConnection`) | no |
| B. A `DataSource` aware of Spring's transaction | no | the store's own `setAutoCommit`, `commit` and `rollback` act on the app's transaction through some proxies and not others | **yes**: existing apps with such a `DataSource` would silently change |
| C. A callback (`stores.inTransaction(c -> …)`) | yes | the platform owns the transaction, so it cannot join Spring's | no |

**A.** It is already the pattern of `PostgresLoginConnectionStore.onConnection`, explicit in the code that uses it, and needs no Spring.
`PostgresFieldStore.onConnection(c)` and `PostgresValueStore.onConnection(c)` return a store bound to the caller's connection; `FieldValues` and `FieldDefinitions` get a light copy bound to it.

```java
// without Spring
c.setAutoCommit(false);
saveMyRow(c, …);
values.in(c).claim(ref, given);
c.commit();

// with Spring, inside @Transactional
Connection c = DataSourceUtils.getConnection(dataSource);
try { values.in(c).claim(ref, given); } finally { DataSourceUtils.releaseConnection(c, dataSource); }
```

### 1.3 Rules of a bound store

1. It **never** calls `commit`, `rollback()` without a savepoint, `setAutoCommit`, `setTransactionIsolation` or `close` on the connection.
2. **Auto-commit must be off** and the isolation **READ COMMITTED**; checked at every call, refused before anything is written with the new code `VALUES_TRANSACTION_UNSUITABLE` (definitions: `FIELD_TRANSACTION_UNSUITABLE`).
   REPEATABLE READ and SERIALIZABLE are refused: the retry after `VALUES_CHANGED_MEANWHILE` and the read after `on conflict` would never see the other writer.
3. **Each write runs in its own savepoint.** A refusal (`VALUES_PRIMARY_TAKEN`, `VALUES_CHANGED_MEANWHILE`, a driver error) rolls back to it, so the app's transaction stays usable and what the app wrote stays. Then the same exception as today is thrown. The app decides whether to roll back all.
4. `FieldValues`' five attempts stay: READ COMMITTED takes a new snapshot per statement.
5. `insert`'s loop for "the conflicting writer rolled back" stays inside its savepoint.
6. **Erasing stays out.** A bound `FieldValues.erase` is refused (`VALUES_ERASE_OUTSIDE_LOG`): the erase log has its own transaction, and an erasure rolled back by the app after the log entry was written would leave them apart.

### 1.4 What changes for locks

- The row lock of `replace` and the wait of `insert … on conflict` are held **until the app commits**, no longer for one statement. Two claims of the same primary value wait for each other that long.
- **Deadlocks become possible** between the app's rows and field rows. PostgreSQL ends one (40P01), `VALUES_STORE_FAILED`; the whole transaction must be retried by the app. `saveAll` already locks in key order; for several records the guide says: one order, for example by record ID.
- **Key service calls happen inside the open transaction** (`claim` with sensitive values: up to three calls, each up to its time-out). That holds locks and a pooled connection while a remote service answers. The guide says so; the build offers no preparing step (see open question 2).

**The app must not:** use the bound object after its transaction ended or from another thread; catch a driver error it caused itself and go on; call the key service again in the same transaction; keep it open for a person; open it at another isolation; send a message or erase on the strength of values not yet committed.

### 1.5 Tests that prove it

1. Roll back the app's transaction after a claim → neither its row nor any `fld_` row, and nothing in the history for definitions.
2. Commit → both, and a second connection sees neither before.
3. A `VALUES_PRIMARY_TAKEN` inside → the app's earlier row is still there and can be committed; the next statement works.
4. Two connections claim one new primary value: the second waits, then joins the record when the first commits, and makes its own when the first rolls back.
5. A version conflict inside is retried and succeeds under READ COMMITTED.
6. Auto-commit on, REPEATABLE READ and SERIALIZABLE are refused, with nothing written.
7. A proxy connection that fails the test on `commit`, `setAutoCommit`, `close` or a full `rollback`.
8. Every existing store test run twice: own transaction, and bound.
9. Spring: `@Transactional` with a thrown exception, `REQUIRES_NEW` around it.

### 1.6 Public API

```java
public static PostgresFieldStore PostgresFieldStore.onConnection(Connection c)
public static PostgresValueStore PostgresValueStore.onConnection(Connection c)
public FieldValues FieldValues.in(Connection c)            // same customer, keys, clock, legal holds
public FieldDefinitions FieldDefinitions.in(Connection c)
// SPI, so that in(c) works whatever the store: refused by default, for a store that has no connection
default ValueStore ValueStore.joined(Connection c)         // throws UnsupportedOperationException
default FieldStore FieldStore.joined(Connection c)         // throws UnsupportedOperationException
// codes
FieldValuesError.VALUES_TRANSACTION_UNSUITABLE
FieldDefinitionException.Code.FIELD_TRANSACTION_UNSUITABLE
```

`FieldDefinitions.in` also needs the app's `FieldValuesCheck` to see the transaction: when the check is a `ValueStore`, its joined copy is used; otherwise the app's check as it is.
**Settings:** none. **Schema:** none. The in-memory stores keep the default.

### 1.7 Risks and size

| Risk | Answer |
|---|---|
| Savepoint per write costs two round trips | Only for bound stores |
| A pool or proxy that hides the isolation level | It is read from the connection; a wrong answer is the pool's fault and shows in test 4 |
| A driver error outside PostgreSQL's rules aborts the app's transaction | Rule 3; nothing to do after a lost connection |

**Size:** medium, about 350 lines of code, 600 of tests, one guide section. Both stores' `run`/`inTransaction` helpers become one place.

## 2. Mail through platform-outbound (LV-24.3)

### 2.1 Today, and one finding

- **Token requests** (`MicrosoftTokens`) use the JDK HTTP client: the JVM's proxy options, no proxy sign-in, the JVM's trust store, no address guard.
- **SMTP** (`EmailChannel`, Angus Mail) connects directly: no proxy, its own `SSLSocketFactory` option that the Spring module does not set, no address guard.
- **There is no allow-list in platform-outbound.** The task speaks of one. What exists: `AddressGuard` (cloud metadata always refused; internal addresses unless `allow-internal-addresses`), https only, the proxy with its **bypass** list, the private CA, no redirects. So "a mail host missing from the allow-list" cannot happen today.
  This note uses the guard, and proposes a small allow-list for mail hosts only (2.4), to be decided.
- **Dependencies:** platform-outbound depends on platform-notifications (`SecretResolver`), so notifications cannot depend on it. The link is a port in notifications, wired in `platform-notifications-spring` with platform-outbound as an **optional** dependency.

### 2.2 The setting

| Setting | Default | |
|---|---|---|
| `platform.notifications.mail.via-outbound` | `false` | token requests and SMTP of this server follow `platform.outbound.*`; also per further server, `mail-servers.<name>.via-outbound` |
| `platform.notifications.mail.smtp-proxy` | `NONE` | only with `via-outbound`: `NONE` (direct) or `CONNECT` (an HTTP CONNECT tunnel through `platform.outbound.proxy.*`) |
| `platform.notifications.mail.allowed-hosts` | empty | only with `via-outbound`: when given, the only hosts mail and token requests may go to (exact names) |

Off by default, for new installations too: no installation loses mail on upgrade. `via-outbound=true` without `platform.outbound.installation`, or without the module on the class path, stops the app with a listed problem.

### 2.3 What it does when on

**Token request (https).** Through `Outbound.send`: https only, address guard, proxy with sign-in, private CA, connection pinning, the server's time-outs, answers up to 64 KiB, no redirects. Codes map to those of today:

| `OUT_*` | Notifications code |
|---|---|
| host unknown, cannot connect, time-out, connection lost, proxy errors | `MAIL_OAUTH_TOKEN_UNREACHABLE` (retried) |
| address blocked, proxy sign-in refused, TLS failed, address not secure | `MAIL_OUTBOUND_REFUSED` (new, not retried: someone must change something) |

**SMTP (not HTTP).**

| Part | Behaviour |
|---|---|
| Address guard | yes: host checked before each connection, and the connection goes to the checked address. `allow-internal-addresses` decides about an internal relay, **which most on-premises relays are** |
| Private CA | yes: `TrustBundle` of the installation becomes the socket factory, with host names checked as today |
| Proxy | **direct by default**, also when `platform.outbound.proxy` is set: an HTTP proxy often forbids CONNECT to 25, 465, 587. Only `smtp-proxy=CONNECT` uses it, with its sign-in and its bypass list |
| Security `NONE` | allowed only when plain http is (internal addresses allowed); the password never goes in clear to a public host |
| Time-outs | the mail settings', as today |

The Teams and Slack webhooks stay as they are; they are the same kind of change and were not asked for (open question 4).

### 2.4 Start-up and health

With `via-outbound` the start-up check looks at every configured mail host (and the Microsoft sign-in host) **without connecting**, and lists all problems:

- `…mail.host: not in …mail.allowed-hosts` (and the same for the sign-in host);
- `…mail.host: an internal address, but platform.outbound.allow-internal-addresses is false`, only for literal addresses and names that resolve at start;
- `…mail.smtp-proxy: CONNECT, but platform.outbound.proxy is not set`;
- `…mail.security: NONE needs platform.outbound.allow-internal-addresses`.

A name that does not resolve at start is a warning, not a stop: DNS may come later. The first two **stop the app** only because someone switched the setting on. While running, a blocked address is `MAIL_OUTBOUND_REFUSED` on the destination's health, and monitoring's `channel-mail` check follows the same path.

**Install guide:** a section "Mail through the outbound settings": what it changes, that it is off, firewall lines for each way, the relay case, how to try it (Test, then read health), how to switch back (one setting, restart).

**Schema:** none.

### 2.6 Risks and size

| Risk | Answer |
|---|---|
| An internal relay is blocked after switching on | Start-up lists it; the guide names `allow-internal-addresses` first |
| STARTTLS over a custom plain socket factory: Angus upgrades the socket itself | Test against real STARTTLS and implicit TLS servers, host name mismatch included; a wrong setting must fail, never fall back to plain |
| A CONNECT tunnel held open by an idle proxy | one connection per message set as today; time-outs apply to the tunnel too |
| `sockets()` opens a raw TCP door in platform-outbound | only the guard's addresses; documented for mail; not used by integrations |

**Tests:** proxy with and without sign-in, with and without bypass; metadata and internal addresses refused; DNS answer changing between check and connection; STARTTLS / TLS / NONE through each way; private CA; off = byte-for-byte today's path (existing tests untouched); every start-up problem.

**Size:** large, about 700 lines of code and 900 of tests, three modules. It could be two steps: token requests first (small, about a third, no socket work), SMTP second.

## 3. Open questions

1. **LV-25.2:** is `in(Connection)` enough for both apps, or does one need a Spring bean that finds the current transaction itself? Recommendation: `in(Connection)`; a three-line helper in the guide.
2. **LV-25.2:** key service calls inside the transaction: acceptable? Recommendation: yes for 1.3.0; a `prepare` step (seal before, write inside) only if an app measures long locks.
3. **LV-24.3:** is `allowed-hosts` wanted, as there is no allow-list today? Recommendation: yes, small as it is, since the apps' agreement speaks of one; otherwise drop the setting and its start-up line.
4. **LV-24.3:** Teams and Slack the same way? Recommendation: in the same build only if the apps want it; token requests and webhooks would share one port.
5. **LV-24.3:** build in two steps? Recommendation: yes, token requests in 1.3.0, SMTP in 1.4.0, unless an app needs SMTP through a proxy now.

## B. Fixes, in this order

1. **LV-24.1, privacy, first: recipients of one notice see each other's address.** `platform-notifications`, `email/EmailChannel` puts every recipient in one message's `To:` (around line 210). Send **one message per recipient** (each sees only their own address), with the same content and the same per-message headers. A failure for one recipient must not stop the others; record each delivery and failure per recipient the way the module already records one. Teams and Slack channels: check they don't leak recipients in the same way; fix the same way if they do. Tests: two and three recipients → that many messages, each with exactly one address; no address of another recipient anywhere in a message (headers or body); one bad address → the others still sent.
2. **LV-24.7: a new, empty keyed erase log is refused at start.** `platform-erase-log`, `EraseLog`: `pending()` calls `requireSealed(false)`, so a keyed log with no entry yet refuses with `ERASE_LOG_NOT_SEALED` before its first entry seals it, though the class comment and the guide say a new log is sealed at its first entry. Make starting (and `pending`, `verify`) on an **empty** keyed log work: no entries means nothing to verify and nothing pending, and it is still sealed at its first entry as now. A keyed log **with** entries and no seal still refuses, exactly as now. Tests: app start on an empty keyed location; first entry seals it; a log with entries and no seal still refused; the seal check after a seal unchanged.
3. **LV-22: usage-ledger hash chain breaks with a time finer than a microsecond.** `platform-licensing`, `jdbc/PostgresUsageLedger`: PostgreSQL keeps microseconds; a time with nanoseconds hashed before storing gives a different hash after the round trip. **Inside the ledger**, truncate `recorded_at` to microseconds before hashing and storing (`ChronoUnit.MICROS`), so callers need not. Entries already stored are unchanged (they were stored and hashed with what the database kept, or they were already broken: say which in the report and how a broken one shows). Tests: an entry with a 100 ns time appends and verifies; on a fake clock with nanoseconds; the chain over many entries still verifies. Check the erase log, the identity audit and any other hash chain in the repo for the same fault, and fix each the same way in this task (list them in the report).
4. **LV-24.8: replay below the stored position.** `platform-erase-log`: after a restore of the file storage alone, replay does not re-apply entries below the stored position, so verify fails. Decide with a test what "correct" is: the guard and the guide (item 5) say database and storage are restored together; when only one is restored, the startup check must **say so clearly** (which one is behind, what to do) instead of failing verify later with a chain message. If re-applying the missing entries is safe and already supported by the apply step, do that; otherwise the clear refusal. Record the choice and the reason in the report.
5. **LV-24.9: the guide.** `docs/install/erase-log.md` (and the backup part of setup.md if it has one): restore the **database and the file storage together**, from backups of the same time; what the startup check says when they don't match; the steps to fix it.

## Why

`KeyService.unwrap` opens one wrapped data key per call and `FieldValues.readSensitive(RecordRef)` reads one record per call, so a results page of 25 records is 25 key-service calls. Fingerprints already batch (`KeyService.fingerprints`, one Vault `hmac` call with `batch_input`); opening has no batch.

## B. Build

1. **`KeyService.unwrapAll(CustomerId customer, List<String> wrapped)`**, a new `default` method:
   - returns one result per item, **in the same order**: a new result type in `com.documentplatform.crypto` (for example `final class Unwrapped implements AutoCloseable`) that holds either the data key (32 bytes) or the `CryptoError` of that item. `close()` wipes the key; `toString()` shows neither key nor wrapped value. A list of them is closable as a whole (a helper, so a caller wipes a page in one call).
   - **an item fails as that item**: `CRYPTO_CIPHERTEXT_INVALID` (changed, or wrapped for another customer), `CRYPTO_KEY_DISABLED` (version below the lowest usable) — the same mapping as the single `unwrap`.
   - **the whole call throws** (as `unwrap` does) when the key service is away, refuses the login or permission, times out, or answers with something that is not one result per item.
   - empty list → empty list, no call. More than **`KeyService.MAX_BATCH = 100`** items → `IllegalArgumentException` before any call (no new error code; new enum constants could break callers' switches). A null item → `NullPointerException` before any call.
   - the default implementation loops over `unwrap`, catching the per-item errors above and rethrowing the others, so every existing `KeyService` keeps working.
2. **`VaultKeyService.unwrapAll`**: **one** Transit `decrypt` call with `batch_input`, under the module's existing time-out and retry rules.
   - Vault answers a batch with some failed items with HTTP 400 unless `partial_failure_response_code` is given. Send `partial_failure_response_code: 200`, and still read `batch_results` from a 400 reply (every item failed). Check this against the Vault 1.21.4 Transit docs (source-driven: cite the page in the report) and prove it with the real Vault in the tests, not only with a mock.
   - map each item's `error` with the same logic as the single unwrap's check (share the code; don't copy it).
   - one result per item or the call throws `CRYPTO_KEY_SERVICE_ERROR`.
3. **`InMemoryKeyService`** (testkit): a real batch (one counted call), so app tests can assert "one call per page".
4. **Every class that wraps or forwards a `KeyService`** (grep for it: crypto-spring, monitoring, erase log, setup) must not hide the batch: a delegating `KeyService` forwards `unwrapAll` to the one it wraps.
5. **`FieldValues.readSensitive(List<RecordRef> refs)`**, a new overload:
   - one result per ref, same order; for each ref exactly the checks and the outcome the single `readSensitive(ref)` has (scope, entity, product, record type, a missing record), but a failure of one ref is that ref's result, not an exception for the page. A small result type (for example `SensitiveRead`: the ref, then the opened `RecordValues` or the `FieldValuesError` the single read would have thrown); `toString()` shows no value.
   - the key-service calls: **one `unwrapAll` per customer** in the list (a page normally has one), never one per record. The whole page fails only when the single read would fail for a reason that is not about one record (key service away, store failure).
   - same limit, 100 refs; empty list → empty list, no call.
6. **Docs:** `docs/design/crypto.md` and the fields design: the batch methods, the limit, the per-item errors; `docs/releases/platform-core-v1.1.0.md` (what's new, "additive only, no change for callers of 1.0.0", the BOM line); the switch-over guide gets one line under crypto and fields pointing to the batch calls. CHANGELOG if the repo keeps one.

## C. Tests (asked in SDV-48, and more)

- order kept, for 1, 25 and 100 items; 101 refused before any call; empty list makes no call;
- a mixed list: good items open, a changed item and an item wrapped for another customer each fail as themselves (`CRYPTO_CIPHERTEXT_INVALID`), the rest still open;
- a version below the lowest usable fails as `CRYPTO_KEY_DISABLED`, the others open; items of different key versions in one list open;
- key service away / time-out / permission denied: the whole call throws, nothing half-returned;
- **the real Vault**: exactly one `decrypt` call per `unwrapAll` (count it), the partial-failure reply, and the all-failed reply;
- `FieldValues.readSensitive(list)`: matches the single read record by record (same values, same errors, a ref of another entity refused as the single read refuses it), one `unwrapAll` per customer, a missing record as that record's result;
- results wipe their keys on close; no key, token, wrapped value or field value in any `toString`, exception or log;
- StableNamesTest: the 1.0.0 rows unchanged; the new signatures added.

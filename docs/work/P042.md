## B. Review — every area, and say what you checked even where you found nothing

1. **Sign-in and admission (identity):**
   - token and claim handling;
   - `PushCaller` (client ID claims, entity and source claims, `cert-sha256` bindings, both required, the cache);
   - `MachineEntityBindings`;
   - login-connection drafts, test sign-in and rollback;
   - the http-issuer rule for local test servers (development licence);
   - entity selection;
   - group grants and platform-level grants (`*` rows), and separation of entity and platform roles;
   - neutral messages to callers, against exact causes in logs.
2. **Setup:**
   - parsing of every input file (licence, trusted keys, product roles, sign-in, role mapping, client bindings, profiles): size limits, encodings, CSV quoting, injection into SQL or logs;
   - the secrets-looking refusal;
   - the transaction and lock;
   - `--replace-connection`, `--remove-unlisted-grants` and `--no-customer-keys` with `customerKeys: required`;
   - the Vault set-up policy can't delete keys;
   - the run log.
3. **Secrets and leaks:**
   - every path from a secret, token, key, document content or field value to a log, exception, `toString`, result, metric, health output, diagnostic bundle or API error;
   - `SafeText` and the bundle's scrubbing: try to beat them (encodings, JSON inside properties, multi-line values, URL forms).
4. **Crypto:**
   - AES-256-GCM use (nonce uniqueness, AAD binding of customer, entity, record and item);
   - the envelope and record-envelope formats;
   - the HMAC fingerprints (key separation, length, normalisation);
   - Vault Transit use (token handling, retry, redirect refusal);
   - customer key destruction and the separate offboarding policy;
   - "can't decrypt" paths.
5. **Erase log:**
   - tamper evidence;
   - replay after a backup restore, and the start-up guard;
   - the outside-the-database location (permissions, path handling);
   - `ValueStore.delete` reachable only through an erasure;
   - concurrency between instances.
6. **Licensing:**
   - signature verification (Ed25519, canonical bytes, key IDs, development keys never trusted by a production release);
   - clock and date handling (not-before, grace, expiry);
   - the usage ledger and export chain;
   - that `platform-licensing-issue` is never needed on a customer's classpath.
7. **Notifications:**
   - approval links (token entropy, expiry, single use, binding to the action and the person);
   - webhook addresses (SSRF through the outbound rules);
   - mail sign-in;
   - content rules (no document content or sensitive field in a message).
8. **Integration and outbound:**
   - the SSRF guard: metadata, internal and IPv6 forms, DNS rebinding, pinning, redirects, the proxy and CONNECT;
   - TLS (trust bundle, host-name checks, private CA, mTLS key storage under customer keys, CURRENT/NEXT);
   - signed callbacks (constant-time comparison, time window, replay store);
   - templates (escaping, no expressions, reserved headers, path traversal);
   - polling (same-origin next links and status links, size limits);
   - the watched folder: path traversal, symlinks and junctions, zip or nested content if any, claim races, the trigger parsers (XXE, billion laughs, JSON depth and size);
   - folder export: names, the `.partial` swap, overwrite rules;
   - the scanner adapters (ICAP and clamd answers, fail-closed);
   - profiles: a malicious profile file can't reach secrets, change hosts or run code.
9. **Monitoring and errors:** health and dependency output reachable without sign-in; the bundle's contents and size; reference IDs that can't be guessed; error messages that don't reveal internals to callers.
10. **Model governance:**
    - separation of duties (approver and forbidden roles);
    - insert-only records and the purge function's rights;
    - the digest and configuration check can't be skipped;
    - the documentation pack holds no content.
11. **Database:**
    - every SQL statement uses parameters (search for string-built SQL);
    - the runtime users' rights per schema;
    - the triggers that freeze history;
    - row ownership by customer and entity in every query (prepares for the hosted service's row-level security).
12. **Dependencies and build:**
    - list third-party dependencies with versions, and check them against known vulnerabilities (OWASP Dependency-Check or the GitHub advisory database through `gh api`; say which). Flag any without upkeep;
    - the GitHub Actions workflows: permissions (least privilege), pinned actions (by SHA or trusted version), how secrets are used, the `GITHUB_TOKEN` scope for publishing, and pull requests from forks;
    - the release workflow can't publish an unreviewed commit.
13. **Public API:** after P041, anything public that lets an app go around a safety rule (a test hook, an unsafe constructor, a way to skip a check).

## C. Output

- **`docs/work/security-findings.md`**, one finding per row:
  - an ID (`SEC-n`);
  - the area;
  - a title;
  - a **severity**, using CVSS-like judgement in plain words:
    - **Critical**: exploitable now, with serious harm;
    - **High**;
    - **Medium**;
    - **Low**;
    - **Info**: hardening, not a flaw;
  - where (file and line);
  - what an attacker or a mistake can do;
  - the proof: steps, or the local test's description;
  - the proposed fix;
  - a size: S, M or L.
- A short **"checked and fine"** list per area, so the next reader knows what was covered.
- **Group the fixes** into proposed fix tasks. All Critical, High and Medium findings must be fixed before the integration release; Low by choice; Info noted.

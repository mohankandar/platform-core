## B. Build

### B1. Client certificates for outbound calls (requirement 13)

- **Sign-in type** `MUTUAL_TLS`, alone or together with another sign-in type (for example mTLS plus OAuth2). The OAuth2 token request may use the same certificate.
- **Two sources:**
  - **(a) Uploaded:** a PKCS#12 or PEM certificate with its private key, stored **encrypted with platform-crypto under the customer's keys**, in a new table `int_credential` (integration schema V2).
  - **(b) A customer-managed keystore:** a file path, a password by secret reference, and an alias. Nothing is copied.
- **Shown only as:** subject, issuer, serial, SHA-256 fingerprint, valid from and to. The private key and the file are never returned, logged or put in a result, and the upload is refused unless the key matches the certificate.
- **One credential per integration per entity**, as the standards require.
- **Rotation without downtime:** up to two credentials per integration, CURRENT and NEXT.
  - NEXT becomes CURRENT at the admin's switch, or automatically at a set time. The old one is kept as RETIRED.
  - The Test action can test NEXT before the switch.
  - Every change is versioned and audited like the configuration.
- **Expiry warnings:** `CredentialExpiry.check(now)` returns the credentials that reach 30, 7 and 1 days before expiry (defaults the installation can change) and those already expired.
  - The app turns them into IT notices through its own notifications.
  - Platform-core emits no notifications itself.
  - An expired CURRENT credential refuses the call with `INT_CREDENTIAL_EXPIRED` (SIGN_IN_FAILED).
- **Codes:** `INT_CREDENTIAL_*`: invalid file, wrong password, key mismatch, expired, not yet valid, missing, key service failed, and the destination refused the certificate (from the TLS alert).

### B2. Connection pinning (required before the hosted service)

- The connection must go to the **address that was checked**, not a fresh lookup.
- Use an HTTP client that accepts our own resolver, for example Apache HttpClient 5 with a `DnsResolver` that returns only the checked addresses. If you choose something else, say why.
- Host name verification and SNI stay on the original name.
- Every call uses it: API push, token requests, health, the issuer fetch and callbacks.
- Proxy calls still connect to the proxy. The target check happens before CONNECT, as today.
- The existing behaviour and codes stay; the P023 tests stay green.
- **Test:** a resolver that changes its answer between the check and the connection (rebinding to a metadata address) is not followed.

### B3. Signed callbacks out (requirement 12)

An app tells a configured receiver that a case is done or failed.

- **New kind `CALLBACK`:** a configured receiver address with the same safety rules, a signing secret by reference, and limits.
- **Signing:**
  - header `Platform-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, t + "." + body)>`;
  - header `Platform-Callback-Id: <unique id>`, which the receiver can use to ignore repeats;
  - the body is JSON the app gives, never document content.
- **Delivery:** through an outbox, `int_callback_outbox` (integration schema V2), following the notifications outbox pattern.
  - It is retried with back-off (for example 1 min to 6 h, up to 24 h, defaults changeable) and honours Retry-After.
  - It survives restarts, and a callback goes out at most once at a time.
  - Every attempt is classified like an API push.
  - When it gives up: `GAVE_UP`, which the app can list and resend.
- **Secret rotation:** the receiver may accept two secrets during a change. The sender signs with the current one, and the docs say how to rotate.
- **Verifying callbacks in:** `CallbackVerifier.verify(headers, body, secrets, tolerance 5 min, seenIds)`, for an app receiving signed callbacks from a destination. It checks the signature in constant time, the time window and repeats. Codes: `INT_CALLBACK_SIGNATURE`, `INT_CALLBACK_EXPIRED`, `INT_CALLBACK_REPLAYED`.

### B4. "Accepted, check later" (202)

- A step may declare that the destination can answer **202 Accepted**, together with:
  - how to read a status reference (a pointer, or the `Location` header);
  - a status call (method plus path template);
  - pointers and values for done, failed and still working;
  - the earliest time to check again (Retry-After, or a default).
- **Outcome:** the engine returns a new outcome, `ACCEPTED`, with a `PendingStatus` (reference, next check time) and no further steps. Later the app calls `CallEngine.checkStatus(stored, pending)`, which makes one call and returns SENT, REFUSED, ACCEPTED (still working) or the usual failures.
- **The engine still never waits or retries.** The app keeps the schedule.
- This can be in a profile (format `/1`, additive). Update the schema and `docs/design/integration-profile-format.md`.

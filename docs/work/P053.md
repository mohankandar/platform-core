# Task P053 — monthly install proof against the newest release

Written 2026-11-24 by the Shared capabilities thread. The owner decided on 2026-11-24 to run the install proof monthly (P047's suggestion), so that a change of GitHub's runner images, PostgreSQL or Vault is noticed before an app or a customer hits it. Read CLAUDE.md, docs/work/README.md, `.github/workflows/install-proof.yml` and docs/work/P047-report.md first. Repo C:\dev\platform-core, branch main. **No release** (CI and docs only).

## A. Start

1. On main, the only uncommitted files may be this task file and `docs/work/README.md` (the new targeted-testing rule in step 4, from the owner). Commit both as the first commit of your branch, and follow that rule from this task on.
2. New branch `build/monthly-install-proof` from main.

## B. Work

1. **Schedule.** Add a `schedule` trigger to `install-proof.yml` for once a month (for example `cron: '17 6 3 * *'`, a quiet time). The manual and release triggers stay as they are.
2. **Newest release.** A scheduled run has no input, so the workflow finds the **newest published, non-candidate tag** `platform-core-vX.Y.Z` itself (from `git tag`, or the GitHub releases API), and runs the full proof on `ubuntu-latest` and `windows-latest` against it, exactly as for a candidate. Never against a snapshot or an `-rc` tag.
3. **When it fails.**
   - The run is red, as usual.
   - It also opens **one GitHub issue**, with the `install-proof` label, the version, the failed job and step, and a link to the run, so the failure is seen without anyone watching Actions. If an open issue with that label already exists, it comments on it instead of opening a second one.
   - Use the workflow's own `GITHUB_TOKEN` with `issues: write` and nothing more (least privilege, SHA-pinned actions, as the rest of the workflows).
4. **Nothing else changes:** no skips, the same steps as the release proof.
5. **Docs.** Add a short "Monthly install proof" paragraph to `docs/work/README.md` (what it does; that a red run or an `install-proof` issue gets a fix task) and to `docs/design/` where the CI rules are described.

## C. Merge and prove

- Merge the PR with green CI, using the README's stop-on-failed-check line.
- Then start the workflow once **by hand without a version**, the way the schedule would. It must pick the newest release (1.0.0 today) and pass on both systems.
- **To prove the failure path,** run it once by hand against a deliberately wrong version input (for example `0.0.0`): the run fails early and opens (or comments on) the issue. Then close the issue.

## Report

docs/work/P053-report.md per docs/work/README.md, with:
- the schedule;
- the runs (the by-hand run that passed, the failure-path run);
- the issue number;
- the line "No other product's name or behaviour in code".

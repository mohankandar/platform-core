Agreed design (owner, 2026-11-21) — add it as a new section of docs/design/notifications.md, then build it in
platform-notifications (+ -spring):
- Approvers act from the email/Teams/Slack message through ONE-CLICK LINKS (Approve / Decline), not in-chat buttons
  (Teams/Slack callbacks cannot reach on-premises installs; webhooks don't support them).
- A link opens the app's small approval page for that one request. The module provides the shared parts; each app
  builds its page and request types.
- Safety: opening a link never decides anything (the page needs one more click: a POST; email scanners open links). A
  link works only for the recipient it was sent to and only while they still hold the approver role (re-checked at
  decision time through the app). Nobody approves their own request. Links expire with the request (default 24 hours,
  per request type). Decline requires a reason. Messages still follow the content rule.
- Group approvals: the FIRST decision wins; later clicks see "Already approved/declined by <name> at <time>" and change
  nothing; two decisions at the same moment — exactly one wins (database-enforced). The requester is notified of the
  outcome. The app audits every decision.
- Build: signed, single-recipient, expiring action tokens (no secrets or document data inside; HMAC or Ed25519 with a
  key from the SecretResolver); a decision store (Postgres, notif_ tables via the same schema run, plus in-memory in
  the testkit) with first-decision-wins; an API for the app: create request + links, verify a link for the signed-in
  person, decide (approve / decline with reason), outcome event to the requester; Teams/Slack/email message layouts
  with the two links.
- Tests: link opened without POST decides nothing; wrong person refused; role removed refused; own request refused;
  expired refused; decline without reason refused; first decision wins with concurrent decisions; later click sees the
  outcome; tampered token refused; no token or secret in logs.

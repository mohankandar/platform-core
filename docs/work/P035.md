# Task P035 — strength check, step 1: tick every design rule off against the code (read-only)

Written 2026-11-23 by the Shared capabilities thread. This is step 1 of the four-step strength check before the **integration release**, which both apps will pin (board LV-11 and LV-12). Read CLAUDE.md and docs/work/README.md first. Repo C:\dev\platform-core, branch main (`0.6.0-SNAPSHOT`, released up to `platform-core-v0.5.0`).

**This task changes no code.** It produces the list of what is built, what is tested and what is missing, so that step 2 can close the gaps. Be strict: a rule counts as done only when code does it **and** a test proves it.

## A. Start

1. On main, the only uncommitted files may be this task file, `docs/design/integration-module.md` and `docs/design/monitoring.md` (the P028 and P032 decisions sections). Commit them as they are, through the report's PR.
2. New branch `docs/p035-tick-off` from main. Nothing else changes in this task.

## B. Work

### B1. Tick-off, design doc by design doc

For **every** file in `docs/design/` (case-fields, crypto, erase-log, error-codes, integration-module, integration-profile-format, integration-standards, licensing-file-format, licensing, model-governance, monitoring, notifications, setup), go through it section by section and list **every rule**. That means every "must", every decision, every refusal, every number or default, every "never", and every decided answer in the decisions sections.

Give each rule:
- an ID (`<doc>-<n>`, for example `setup-14`);
- one line in your own words;
- a status:
  - **DONE**: code and a test that proves it; name both;
  - **UNTESTED**: code but no test that proves it;
  - **PARTLY**: say what is missing;
  - **MISSING**;
  - **DIFFERENT**: the code does something else; say what. This includes rules a later decision changed: say which decision, and check the code follows the later one;
  - **APP-SIDE**: the design gives it to the app, so there is nothing here to check. Name the app-side item.

A rule that is only in a task report and not in a design doc is still checked. Search the decisions sections of each `docs/work/PNNN-report.md` for decisions that should be in a design doc and aren't, and list those as **DOC GAP**.

### B2. Cross-checks

1. **Install guides** (`docs/install/*.md`) against the code: every property name, file format, command option, refusal code and default in a guide exists in the code with the same name and value. List any differences.
2. **Error catalogue:** every refusal or failure the code can give is a `PlatformCode` in the catalogue. Known gap from P032 question 2: the Spring startup-settings messages (`*_SETTINGS_INVALID`) are exception prefixes, not codes. List them all.
3. **Never-leak rules:** list every place where a secret, token, key, document content or field value could reach a log, message, result, metric, bundle or exception, and say which test covers each. Any place without a test is a gap.
4. **Schemas:** each Flyway run (identity, licensing, notifications, fields, erase log, integration, model governance, and any other) has the DML-only runtime user's rights documented and tested, and a start-up verify. List any run without both.
5. **Product independence:** confirm the name guard covers every module, including those added after P030 (`platform-outbound`, `platform-errors`, `platform-monitoring`, `platform-model-governance` and their `-spring` / `-testkit` modules).
6. **Public API surface per module:** list the public types an app is meant to use. Mark anything public that looks internal, as candidates to hide before the integration release. Nothing is changed now.

### B3. The gap list

Write `docs/work/gaps.md`, one row per gap (every UNTESTED, PARTLY, MISSING, DIFFERENT, DOC GAP and cross-check finding), with:
- the ID and rule;
- what is missing;
- a **severity**:
  - **A**: wrong or unsafe; must be fixed before the integration release;
  - **B**: missing or untested; should be fixed before it;
  - **C**: polish or docs; fine to fix after;
- your proposed fix in one line;
- a size: S, M or L.

Group the rows into proposed step-2 tasks (the closing tasks), so that each group fits in one task.

## C. Merge

Bring `docs/work/gaps.md` and the report to main through one PR with green CI, using the README's stop-on-failed-check line. No release.

`docs/work/P035-report.md` per docs/work/README.md, with:

- the cross-check results;
- the A / B / C totals;
- the proposed step-2 task groups;
- the line "No other product's name or behaviour in code" (confirmed by the guard and your read).

## B. Findings

### FIX-B: SEC-3, SEC-4, SEC-5, SEC-49

- **SEC-3:** the erase log's chain gets a keyed MAC under a key in the key service, so someone who can write the log folder can't forge erasures. Existing logs: a versioned migration, never a silent rewrite. The tamper check names the first bad entry.
- **SEC-4:** a database restored while the app keeps running is noticed. Check at least per erase-log write and on a schedule; when the database's position is behind the log's, stop taking work and replay first. The detection itself is the design's choice.
- **SEC-5:** no public class can erase a field value without the erase log. Close every path the finding lists, and add a build test that no public API outside the erase-log flow can reach a delete.

### FIX-C: SEC-2, SEC-30, SEC-48

- **SEC-2:** the set-up policy can't trim or delete key versions. Only the offboarding policy can. Add a negative test against a real Vault (Testcontainers), and correct the docs.
- Apply the SEC-30 and SEC-48 hardening as proposed.

### FIX-F: SEC-8, SEC-10

- **SEC-8:** a signed callback can't be resent under a new ID: the ID is inside the signed bytes, and the verifier's replay store keys on what was signed. Bump the signature version (`v2`). The verifier accepts v1 only when the installation turns that on, and v1 is off by default (nothing is released to apps for integration yet).
- **SEC-10:** a secret reference is checked against the integration's own customer and entity scope, at save and at use. One entity's integration can never name another's secret. The secret-reference naming rule is documented.

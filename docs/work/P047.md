## B. Work

### B1. A release candidate

Release **`platform-core-v1.0.0-rc.1`** per the routine (version `1.0.0-rc.1`), so the install proof uses **published artifacts only**, never a local build.

### B2. The sample app (in the repo, not published)

`examples/sample-app`: a minimal Spring Boot 4.2 app that **uses every module the way its install guide says**:
- identity with setup;
- licensing in read-only and in enforcing mode;
- notifications (mail to a local test server);
- fields;
- crypto with Vault;
- the erase log;
- integration (one folder export and one API push, to the testkit's mocks or a local stub);
- monitoring;
- model governance;
- errors.

It takes platform-core **only from GitHub Packages at a given version**. It's built and tested in its own job, never in the reactor, and it is not in the BOM.

### B3. The install-proof workflow

`.github/workflows/install-proof.yml`, run on a manual trigger with a version input, and by the release workflow for every `-rc` tag. **Two jobs, `ubuntu-latest` and `windows-latest`.**

Each job follows the install guides **as a customer's IT would**, step by step:
1. **PostgreSQL and Vault** the way the guides tell a customer:
   - on Windows: the PostgreSQL installer or package and the Vault Windows binary, **no Docker** (Windows runners have no Linux containers);
   - on Linux: the same, or containers where the guide allows them.
2. Create the database users with the rights the guides list (owner and DML-only runtime users per schema).
3. Run every **schema step** (each module's Flyway run with its own history table, notifications included).
4. Write the Vault policies from the guides, and log in with the set-up policy.
5. Run the **setup command** with sample input files (a development-signed licence from a test key built into the sample app, sign-in file, role mapping, client bindings, a profile).
6. Start the sample app with the **DML-only** users. Readiness must be UP, and every dependency check WORKING.
7. Run a smoke script:
   - a test sign-in against a local mock issuer;
   - an entity activation;
   - a field value encrypted and searched;
   - an erasure through the erase log, plus a restart that replays it;
   - a folder export with its manifest;
   - a model gate refusal and an approval;
   - a diagnostic bundle checked for no secrets;
   - one notification to the local mail server.
8. Run the start-up refusal checks: a stopped database, then a missing customer key. Each gives its documented code.

**Every step that differs from its guide is a finding.** Fix the guide (or the code, if the guide is right) in this task, then release another candidate (`-rc.2`, …) and run the proof again, until both jobs pass with no workaround.

### B4. The switch-over guide

Write `docs/install/switch-over.md`: how an app adopts `platform-core-v1.0.0`, generic and module by module. It covers:
- prerequisites: Spring Boot 4.2 and Java 21;
- what to add (dependencies from the BOM);
- which schema runs and in what order;
- the setup inputs;
- the settings;
- what the app still owns: its audit, screens, schedules, notification events, test sets, profiles;
- the identity-only apps' bump from earlier versions;
- the order the apps should switch modules in.

Every step links to the install guide that details it.

### B5. Final checks before 1.0.0

- No open **A or B** row in `gaps.md`.
- The advisory check (as in P046): no open High or Critical in compile or runtime scope.

If any check fails, stop and report; don't release 1.0.0.

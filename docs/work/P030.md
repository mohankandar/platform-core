### B2. The profile format `platform-integration-profile/1`

The format any API owner publishes next to its spec, so any app can talk to that API by configuration.

- **What a profile holds:**
  - format (`platform-integration-profile/1`), name, version, the API it describes (title + version);
  - direction and kind;
  - steps or a packaging preset, with templates and response reads;
  - sign-in: the allowed types and what the installation must supply;
  - the health check with its rules;
  - classification rules for answers and for health;
  - the error-code pointer;
  - limit defaults;
  - the app values and field keys it expects, with which are required;
  - notes for IT.
- **Never in a profile:** an address, a secret, a client ID, an entity, or any customer data. The installation adds those.
- **Files:** JSON Schema at `platform-integration/src/main/resources/schema/platform-integration-profile-1.schema.json`; the format in plain words at `docs/design/integration-profile-format.md`, with the versioning rule: `/1` changes only by additions that old profiles still pass; anything else is `/2`, and the validator refuses formats it doesn't know.
- **Validator:** `ProfileValidator`. It checks the schema and the same rules `ConfigCheck` applies (placeholders, reserved headers, rule shapes). Every problem has a code (`INT_PROFILE_*`) and a JSON pointer, never a value.
- **Loader:** a loader that reads a profile **from a file path the app gives**; nothing is shipped on the classpath. Then `IntegrationConfig` is built from the profile plus the installation's part (address, sign-in, entity, product), and the result goes through the normal save checks.
- **Mock:** `MockDestination` loads **any** profile, and optionally an OpenAPI file:
  - routes, request checks and answers from the response schemas;
  - switches derived from the profile's rules: busy, down, a refusal with a code, already received, sign-in refused, health busy, health down.
- **Contract-test kit** in `platform-integration-testkit`, for an API's owner to run in its own CI:
  1. `ProfileContract.checkAgainstSpec(profile, openapi)`:
     - every operation the profile uses exists with the same method, path, required headers and fields;
     - every error code the spec lists maps to a rule;
     - the profile's requests validate against the request schemas.
  2. `ProfileContract.checkAgainstServer(profile, baseUrl, signIn)`: a live check of health, sign-in and one refusal, no real data.

  Both report every problem; neither knows any product.
- **Setup:** an optional per-product `"integrationProfiles": [{ "name", "file", "tag" }]` in `platform-signin/1`:
  - Setup validates each file in preflight; the `tag` must be present, and the profile's own name and version must match.
  - The plan and the run log list each profile as "checked".
  - Setup stores nothing for them; the app's integration screens use the file later.
  - Refusals: `SETUP_PROFILE_INVALID` and `SETUP_PROFILE_TAG_MISSING`, with the file and the JSON pointer.
  - Older sign-in files still load.
- **Tests:**
  - at least two made-up profiles with different shapes, e.g. `acme-archive-v1` (two-step) and `example-dms-v2` (multipart), in test resources only;
  - validator refusals, one per code;
  - the mock driven by each profile for every switch;
  - the contract kit passing, and failing on a planted spec change;
  - setup's profile check;
  - an end-to-end send for each profile.

### B3. CI (GitHub Actions)

- `.github/workflows/ci.yml` on every push and pull request: JDK 21; `mvn -B verify` on `ubuntu-latest`. On that runner the Testcontainers PostgreSQL tests and the 3 end-to-end TLS tests must **run, not skip**: the build fails if any of them is skipped (check the Surefire reports). The product-name guard is part of `verify`.
- `docs/work/README.md` routine, new merge steps:
  1. push the branch;
  2. open a PR with `gh pr create`;
  3. wait with `gh pr checks --watch`;
  4. merge only when green (`gh pr merge --rebase --delete-branch`).

  If `gh` is missing or not signed in, stop with the PR open and say so. No local merges into main.
- Remove `mvn install` from the routine. Local checks use `mvn verify` only.

### B4. Releases and publishing

- `distributionManagement` → GitHub Packages, `https://maven.pkg.github.com/mohankandar/platform-core`.
- `.github/workflows/release.yml`, run on a pushed tag `platform-core-v*`:
  - check that the POM version equals the tag's number and has no `-SNAPSHOT`;
  - run `mvn -B verify`;
  - run `mvn -B deploy` with `GITHUB_TOKEN` (`packages: write`);
  - create the GitHub release from `docs/releases/<tag>.md`.
- **Release routine** in `docs/work/README.md`:
  1. A PR sets the version to `X.Y.Z` (`mvn versions:set`) and adds `docs/releases/platform-core-vX.Y.Z.md`, with:
     - the modules;
     - the design docs implemented;
     - breaking changes;
     - the database schema versions;
     - the "No other product's name or behaviour in code" line.
  2. CI is green, the PR is merged, and the merge commit is tagged `platform-core-vX.Y.Z` and pushed. The release workflow publishes.
  3. A second PR moves main to the next `-SNAPSHOT`.

  Tags are never moved or reused.
- **Build-a-tag script**, `scripts/build-release.ps1` plus `scripts/build-release.sh`: for offline builds and install bundles; it names no product.
  - Arguments: `-Tag <tag> -Repository <local maven repo path>`.
  - It checks out the tag in a temporary worktree and runs `mvn -B install -DskipTests -Dmaven.repo.local=<path>`.
  - It refuses a tag that is not `platform-core-v*`, and it never touches `~/.m2`.

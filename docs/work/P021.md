## C. Erase log — new module `platform-erase-log` (+ -testkit, + -spring), shared by LexaVault and Vero

Per docs/design/erase-log.md:

- **Entry (no values):** entity, product, record/case ID, what was erased (an app-defined kind, e.g. `document`, `redacted-copy`, `case-fields`, `export-copy`), when, by which rule or person, the app's audit record ID; a sequence number and a hash chained to the previous entry (tamper-evident). Refuse anything that looks like a value field.
- **Store outside the database it protects:** a store interface, with a default **append-only file store** on a configured location (meant for separate storage, backed up separately), written durably before the erase is acted on. Document the install rule (the location must not be inside the database's own storage or its backups). Optionally a separate-database store behind the same interface if simple; say which you built.
- **Write order:** log entry written durably first, then the app (or platform-fields) erases and records the **applied position** in its own database in the same transaction.
- **Guard after a restore:** at startup, if the database's applied position is behind the log's head, the system must **not take work** (a state the app checks, plus a specific code and message: "Restored from backup: run the erase replay before starting work") until replay has run.
- **Replay command:** applies every entry after the database's applied position through **handlers registered per kind** (platform-fields' `FieldValues.erase` is the built-in `case-fields` handler; documents and copies are the apps'). **Safe to run twice** (an already-erased item counts as done). Then the **verify step**: each handler confirms nothing in the log is readable; only then the guard lifts.
- **Retention:** keep entries at least backup retention + 30 days (backup retention default 35 days, setting 30–90 per installation); pruning keeps the chain verifiable from a checkpoint.
- **Spring wiring:** properties (store location, backup retention days), the startup guard, health (log reachable, chain intact, position in step).
- **Tests:** entry with a value refused; chain tamper detected; write order (crash between log write and erase → replay finishes it); restore simulation (database older than the log) → guard blocks work → replay → verify → guard lifts; replay twice is safe; handler failure stops replay with its code; pruning; DML-only user for the position table.

## D. Customer key destruction (crypto, customer exit)

In platform-crypto, per docs/design/erase-log.md "(c)":

- `KeyService.destroyCustomerKeys(customer)`: destroys the customer's wrapping and fingerprint keys (Vault Transit: allow deletion, then delete). **Irreversible**, so: an explicit command (`crypto destroy-customer-keys`) that requires typing the customer ID back as confirmation, refuses without it, is run with the setup-only login, and writes an audit-ready result.
- Result data for the **offboarding certificate**: customer, the keys destroyed (names and versions), date and time, who ran it. No key material.
- Document in docs/design/crypto.md: after destruction, every record, value and backup of that customer is unreadable; note that key-service backups (e.g. Vault snapshots) hold the keys until they expire, so their retention must also be within the agreed period.
- Tests (Testcontainers Vault and in-memory): destroy → decrypt and fingerprint refused with specific codes; confirmation missing or wrong → refused, nothing destroyed; the runtime policy cannot destroy; result contains no key material.

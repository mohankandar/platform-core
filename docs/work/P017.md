Build module platform-fields (package com.documentplatform.fields, plain Java core; add to build and BOM), per
docs/design/case-fields.md:
- Field definition model per entity and product: key, label, type (TEXT, NUMBER, MONEY with one currency per field,
  DATE, EMAIL, UUID, DROPDOWN up to 100 values, ADDRESS structured street/city/state/ZIP with a country part ready,
  CUSTOM_PATTERN), rules (required, exact/min/max length, pattern, normalisation), flags (primary, searchable,
  sensitive, multi-value, displayable), display order, active. App-only settings attach by key (an extension map),
  not in the model. Name and address fields default to sensitive.
- Validation and normalisation of values for every type, with stable error codes and plain messages that never echo
  a sensitive value.
- Rules: key and type never change once values exist (the store answers "values exist" through an app-supplied
  check); label may change; removing = deactivating, never deleting.
- Export/import file format (platform-fields/1, JSON) so Vero can import LexaVault's field list; matching by key;
  import reports create/unchanged/conflict (type differs) and never changes an existing field's type.
- Delivery format for LexaVault → Vero: each field as key + type + value (list for multi-value); a verifier on the
  receiving side refusing unknown keys or type mismatches with specific codes.
- Postgres storage of definitions (fld_ tables, own Flyway run db/platform/fields with history table
  fld_schema_history, run only by the schema step; startup only verifies; DML-only runtime user) + in-memory testkit.
- Mapping from LexaVault's current types (NUMERIC, ALPHANUMERIC, ALLOW_LIST, …) and Vero's documented in
  docs/design/case-fields.md.
- Do NOT build value storage or search yet (next task: encrypted sensitive values with exact-match fingerprint
  search, docs/design/case-fields.md rule 6).
- Tests for every type and rule, import/export round trip, delivery verifier, no sensitive value in any message or

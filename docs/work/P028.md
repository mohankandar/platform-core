**What it is for:** an app's own push API (a sender calls the app) has verified the caller's token, or its client certificate, with its usual server setup. It then asks platform-core: *which entity and which sending system is this caller, and may it call?* Platform-core answers from the client bindings that setup loads (P029). The app's controller calls it on every request.

## B. Build

### B1. `PushCaller` (identity-core API, Postgres and in-memory versions)

- **Input,** one of two:
  - **(a) A verified token:** issuer, audiences and claims (the app's JWT decoder has already checked the signature and expiry).
  - **(b) A verified client certificate:** an `X509Certificate` the app's TLS layer has already checked against the customer's CA.
- **Configuration per product** (`PushCallerSettings`; Spring properties in identity-spring):
  - the claim names to read the client ID from, in order. The default is `client_id`, `azp`, `cid`, `sub`, because login systems differ;
  - optional names of **entity** and **source** claims. If configured and present, they must equal the binding, or the call is refused. When not configured, entity and source come from the binding alone;
  - the required API audience: the product's `apiAudience` from the login connection.
- **Lookup:**
  1. issuer → the customer's ACTIVE login connection for this product (`ConnectionKey`);
  2. client ID → the ACTIVE binding (`idn_machine_binding`), whose entity must be ACTIVE.

  The result is a **`PushCallerIdentity`**: customer, entity (slot ID and UUID), source key, client ID, and how the caller was identified (token or certificate). Add a lookup that returns the source too, beside `MachineEntityBindings`, which keeps its current signature.
- **Client certificates:** a binding's `client_id` may be **`cert-sha256:<64 lowercase hex>`**, the SHA-256 fingerprint of the caller's certificate (DER). This is additive in the client-binding file (6.1); the reader and its rules stay as they are.
  - Two lines with two fingerprints for the same entity and source give a rotation overlap.
  - Certificate-only callers need no token. A product may require **both** (`requireTokenAndCertificate`), and then both must point to the same binding.
- **Refusals:** the caller gets a neutral answer, nothing about why; the log and the IT Admin get the exact cause. Codes:
  - `IDN_PUSH_NO_CONNECTION`: no ACTIVE connection for this issuer;
  - `IDN_PUSH_AUDIENCE`;
  - `IDN_PUSH_NO_CLIENT_ID`;
  - `IDN_PUSH_NOT_BOUND`;
  - `IDN_PUSH_BINDING_OFF`;
  - `IDN_PUSH_ENTITY_NOT_ACTIVE`;
  - `IDN_PUSH_CLAIM_MISMATCH` (an entity or source claim differs);
  - `IDN_PUSH_CERT_NOT_BOUND`;
  - `IDN_PUSH_TOKEN_AND_CERT_DIFFER`.

  A database error throws, and never falls back to a configured entity.
- **Speed:** a small cache (for example 30 s) of positive and negative answers per key. Switching a binding off takes effect within that time, as the docs say.

### B2. Spring (identity-spring)

- A `PushCaller` bean and its properties `platform.identity.push.*`.
- A helper that turns Spring Security's `Jwt`, or the request's client certificate, into the input.
- **No filter that decides on its own:** the app's controller calls it and maps the refusal to its own error answer.
- **Docs:** only trust a forwarded-certificate header from the app's own TLS-terminating proxy, configured by the app. Platform-core reads no headers.

The `LoginConnections` bean gets the fetch without `platform-integration` on the classpath. A test proves it: an identity-only Spring context with a working test sign-in.

### B5. Platform-level grants (board LV-16 item 3)

`product-roles.json` already lists `platformRoles`, but there is no way to grant them.

- **Role-mapping file `platform-role-mapping/1`, additive:** an `entity_id` of **`*`** means "platform-wide for this customer and product". On such a row:
  - the role must be one of the product's `platformRoles`;
  - an entity role is refused on a `*` row, with `SETUP_PLATFORM_ROLE_ON_ENTITY` or `SETUP_ENTITY_ROLE_PLATFORM_WIDE`.
- **Store:** a new table `idn_platform_grant` (customer, product, issuer, group, role), in **identity schema V4** (`V4__platform_grants.sql`; don't edit V1–V3). `idn_grant_history` gets a `scope` (ENTITY or PLATFORM) and allows a null entity for PLATFORM rows, in the same V4.
- **Setup** loads `*` rows like the others (plan, apply, `--remove-unlisted-grants`, history, run log).
- **Admission:** `PlatformGroupAuthorization` gives a signed-in person's platform roles from their groups, for the customer's ACTIVE connection and the product, in the Postgres and in-memory versions. `EntityGroupAuthorization` keeps refusing platform roles through entity grants.
- **Docs:** `docs/install/setup.md` explains in plain words that a `*` row is for roles like a platform operations admin, and who should get them.

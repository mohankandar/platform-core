## B. Build

### B1. Building blocks left from P023 (generic, `platform-integration`)

- **MULTIPART body:** documents + one JSON part; part names, file name and content type from templates; streamed, size limits enforced before sending.
- **Packaging presets** as configuration shortcuts that expand to ordinary steps (no special engine paths): `TWO_STEP` (create, then upload each document), `MULTIPART`, `FILE_PER_CALL` (details in headers).
- **Lists in JSON templates:** one fixed construct for "one item per document" (e.g. `expectedDocuments[]` with `{doc.*}` placeholders inside). Still no expressions or loops beyond that one construct.
- **Field mapping by platform-fields key:** placeholder `{field:<key>}` (e.g. `{field:contract_number}` → `loanId`), values passed by the app in the delivery in platform-fields' delivery format (key + type + value). Type-correct JSON rendering (number, date, boolean). **Sensitive fields:** sent only when the integration's configuration explicitly allows that key (refused at save otherwise, `INT_CONFIG_SENSITIVE_FIELD_NOT_ALLOWED`); never in logs, results or the mock's records (the mock records field names only).
- **Integrity check:** when a step's `read` names the destination's returned checksum / size, the engine compares them with what was sent. Mismatch → `UNCLEAR` / `INT_INTEGRITY_MISMATCH`, attempt used, the stop point reported.
- **Per-step rules** (optional) before the integration's rules.

### B2. New module `platform-integration-profiles` (+ in BOM, root modules, CLAUDE.md)

- Profiles are **data** (JSON resources) named after a published API, loaded by name into an `IntegrationConfig` template the app completes (address, sign-in, entity). No product code, no product package; `NoProductNamesGuardTest` must still pass.

### B3. Profile `sdv-ingestion-v1` (from the pinned spec)

- **Pinned copy:** `platform-integration-profiles/src/main/resources/.../sdv-ingestion-v1/sdv-ingestion-v1.openapi.json` plus `PINNED.md` (source repo, branch or tag, commit, date, spec `info.version`, SHA-256 of the file).
- **Steps:** Vero's two steps (create submission, then upload each document) with the real paths, headers and body fields from the spec; idempotency key per document; read the IDs and the returned checksum for the integrity check.
- **Sign-in:** OAuth2 client credentials; health `/actuator/health/readiness`. Setting `vero.senderIdentity = CLAIMS | LOOKUP` (default CLAIMS): with CLAIMS the install guide says the login server must add `sdv_tenant_id` / `sdv_source_id` for the client; with LOOKUP nothing is needed (Vero 0041). Sender behaviour is the same either way; the setting only changes the checks and the guide.
- **Rules (as data, from the spec's `x-sdv-answers`):**
  - 503 + `SDV-SYS-018` → **BUSY**, no attempt used, Retry-After passed through (Vero setting 1–300 s, default 5; the mock and tests use values across that range);
  - 503 + `SDV-STO-004` → **OUTAGE** (down: a 503 without the busy code; master 2026-11-22), the destination code kept in the result so IT sees why;
  - any other 503 → **OUTAGE**;
  - 401/403 `SDV-AUT-*` → **SIGN_IN_FAILED** (AUT-004 included: a sign-in fault, not busy);
  - 200 "already stored" (the spec's replay field/value) → **ALREADY_RECEIVED**;
  - 409 (same key, different content) → **REFUSED**;
  - other 4xx with a code → **REFUSED** with the code.
  - Derive the table from the spec in a test, so a new code in the spec without a rule fails the build.
- **Health check rules (master decision 2026-11-22, no counting):** Vero's readiness `/actuator/health/readiness` answering **503 with `SDV-SYS-018` or with `Retry-After`** → health **BUSY** (`INT_DESTINATION_BUSY`, Retry-After passed through): the app waits and sends fewer at once, **no pause, no attempt used**. Can't connect, a timeout, or a **503 without the busy code and without Retry-After** → **down** (the app pauses and probes). If `HealthResult` can't carry BUSY and Retry-After today, add it (generic: any profile may give health rules that map to BUSY). Readiness-busy comes in a separate Vero commit, not in `76307d6`: build and test these health rules against the mock now; the pinned spec does not yet show them, so the contract test must not require them (note it in `PINNED.md`). Until Vero's commit lands, readiness 503 without either still means down. The 30-minute busy-spell IT notice is the app's (LexaVault), not this module's; say in the report what the app needs from the result to build it (e.g. when the busy spell started is the app's to track).

### B4. Mock and contract tests

- The testkit's `MockDestination` gets a **spec-driven Vero mode**: routes, request checks (required headers and fields from the pinned spec; refuse a request the spec would refuse, with the spec's code) and answers built from the spec's examples. Switches: working, busy (SYS-018 + Retry-After, e.g. 1, 5, 300), outage (503 without code), STO-004, sign-in refused (AUT-*), already received, 409, health failing. In CLAIMS mode its token endpoint adds the two claims and the mock checks them.
- **Contract tests** (every build, against the pinned copy): every operation the profile uses exists with the same method, path, required headers and fields; every answer code in the spec maps to a rule; the profile's requests validate against the spec's request schemas; the mock's answers validate against the response schemas.
- **End to end:** the profile against the Vero-mode mock for every switch → the right outcome, including health: readiness 503 + SYS-018 → BUSY, readiness 503 + Retry-After only → BUSY, readiness 503 bare → down, readiness unreachable/timeout → down; resume after a failure mid-upload; integrity mismatch; sensitive field refused unless allowed.

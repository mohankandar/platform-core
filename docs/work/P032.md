## B. Build

### B1. The error-code standard (all platform modules)

- **The shape:** an interface `PlatformCode` in a new small module **`platform-errors`** (plain Java, no dependencies), with:
  - `code()`, which keeps today's names (`IDN_*`, `INT_*`, `OUT_*`, `SETUP_*`, `LIC_*`, …; **nothing is renamed**);
  - `kind()`: `REFUSED` (the request is not allowed), `FAILED` (we or a dependency failed), `NEEDS_PERSON` (not a failure: sent to review), or `INFO`;
  - `userMessage()`: plain and safe, saying what the person does, with nothing about accounts or internals;
  - `cause()`: the exact cause for IT and the log, with placeholders for safe details only;
  - `fix()`: what IT does;
  - `supportNote()`: what support tells the customer;
  - optionally `httpStatus()`.
- **Every platform code enum implements it.** That includes `IntegrationCode`, `OutboundCode`, `PushRefusal`, `TestReport.Code`, `LicenceRefusal`, `ResetRefusal`, `UsageError`, `IssueError`, `ApprovalRefusal`, `FailureCode`, `CryptoError`, `CryptoCommand.Code`, `EraseLogError`, the fields codes, `MappingError.Code`, `ClientBindingsFile.Code`, the setup refusals, identity admission codes, and any others found (search for every enum of codes). Missing texts are written now, in plain words.
- **`PlatformError`:** code, user message, cause with its safe details, reference ID (B3), time. `toString` and logging never include anything unsafe; a test plants secrets and content and checks.
- **The generated catalogue:** a build step writes `docs/errors/platform-error-codes.md` and `.json` (code, module, kind, message, cause, fix, support note). Every code is listed once, and codes are unique across modules. **A test fails when the generated file is stale, or when a code lacks a message, cause or fix.** CI runs it.
- **The guide for apps:** `docs/design/error-codes.md`.
  - How an app fits its own codes to the shape. Apps keep their names, for example `LV-…` or `SDV-AREA-NNN`; they implement `PlatformCode`, or map to it.
  - How an app shows the message with its reference, and logs the cause.
  - **The API error format** (requirement 16): `{"code", "message", "reference"}` plus an optional `details` holding safe values only. The `X-Request-Id` header is echoed back, or one is made when missing. Versioning rules for an app's API: `/v1` in the path; within a version only additions; a new version for anything else; at least one release of notice for a version's end.

### B2. `platform-monitoring` (+ `-spring`, `-testkit`): dependency self-checks

- **`DependencyCheck`:** name, group, `requiredAtStartup`, and `check()`. It returns a `CheckResult` with:
  - a state: **WORKING**, **HAVING_PROBLEMS** or **DOWN**;
  - a `PlatformCode`;
  - the exact cause;
  - the fix;
  - when it ran and how long it took.

  A check that throws or hangs past its time limit is DOWN with `MON_CHECK_FAILED` or `MON_CHECK_TIMEOUT`, never an unhandled error.
- **Built-in checks,** each giving a specific cause:

  | Check | Tells apart |
  |---|---|
  | Database | can't reach; login refused; schema version expected vs found, **per platform schema in use** (reuse each module's verify) |
  | Key service | can't reach; login refused; a customer key missing; permission denied on a key; key disabled |
  | Secret store | each configured secret reference resolves (names only) |
  | Login system | the customer's ACTIVE connection's issuer discovery and keys reachable (`OutboundIssuerFetch`) |
  | Licence | missing; signature invalid; another customer's; not started; expiring (days); in grace; expired. Read-only, and it never enforces |
  | Mail / Teams / Slack | each configured channel's settings are complete and its server or address is reachable. Nothing is sent |
  | File locations | a configured path exists, is readable and writable; free space has a warning and a down threshold (defaults 90% and 95%) |
  | HTTP service | for an app's own dependencies, such as a model server or OCR service: a configured address and health path, reachable with the expected answer |
  | Integrations | each enabled destination and source, as P025–P027's health gives it. **Never** `requiredAtStartup`, and **never** part of readiness |

- **Start-up:** `StartupChecks` runs every `requiredAtStartup` check once. If any is DOWN, the app **refuses to start** with that code, cause and fix, one line each (Spring: the context fails with that message). The customer-key check is required at start-up only when the product's `customerKeys` is `required` (P031).
- **While running:** a scheduler runs all checks (default every 60 s, per check changeable) and keeps the latest result. `DependencyStatus` gives the app's Support screen the list.
- **State changes:** each is a `MonitoringEvent` (became DOWN, became HAVING_PROBLEMS, recovered) for the app to route to its notifications. The continuous-failure and summary rules are the notifications module's.
- **Spring health:**
  - liveness never depends on checks;
  - readiness holds only the `requiredAtStartup` checks;
  - an informational `dependencies` contributor lists all checks with state, code and cause;
  - the `integrations` contributor is replaced by entries in it. It is never DOWN because of another system (P025 decision 3).
- **Metrics,** through Micrometer if present, with naming `platform.<area>.<measure>` and tags without values:
  - per check, a state gauge (0 working, 1 problems, 2 down) and the check's duration;
  - per integration, attempts counted by outcome.

  The standard goes in `docs/design/monitoring.md`.
- **Logs:** one key=value line per failure: `code=… ref=… cause="…"`. The reference ID is in the MDC as `ref` while a request is handled. `docs/design/monitoring.md` says how Splunk or Datadog pick it up; the app ships its logs as usual.

### B3. Reference IDs

- `ReferenceId.next()`: short, time-ordered and unguessable, for example `R-` plus 12 base32 characters.
- `FailureLog.record(code, safeDetails)` logs the failure and returns the ID, for the user's message ("… (reference R-…)"), the IT Admin's screen, the log line and a support ticket.
- Every `PlatformError` carries one.

### B4. Diagnostic bundle

`DiagnosticBundle.build(sink)` writes a zip that an offline customer can send us. It holds:
- a manifest with the SHA-256 of each entry;
- versions: the platform modules, and the app's own through a provider;
- Java and the operating system;
- **the configuration with secrets removed:**
  - every value of a property whose name looks secret is removed (`password`, `secret`, `token`, `key`, `credential` and the like);
  - every `SecretRef` value is removed, and only its name is kept;
  - every value that looks like a JWT or a PEM block is removed;
  - addresses are kept;
- the latest results of all checks;
- the last N failures (code, reference, cause, time);
- the schema versions.

**It never holds document content, field values, tokens or secrets.** A test plants each kind in the configuration, the logs and the results, and checks the bundle holds none. A bundle has a size limit.

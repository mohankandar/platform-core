# P013 — identity storage

Read CLAUDE.md, docs/design/setup.md and docs/work/P012-report.md (sections 1 and 5) first. Repo C:\dev\platform-core,
new branch feature/identity-storage from main.

Build (new module platform-identity-jdbc, package com.documentplatform.identity.jdbc; add to build and BOM), per
docs/design/setup.md decisions 1–6:

- SQL under src/main/resources/db/platform/identity/ (tables prefixed idn_: idn_customer, idn_entity,
  idn_login_connection + idn_login_connection_history, idn_group_grant with product_code; own version table), run only
  by the app's schema step as a separate Flyway run with history table idn_schema_history. Startup only verifies tables,
  version and DML rights, with specific codes and messages. No secrets (only secret references), no document data.
- entity_uuid derived from the slot ID (name-based UUID from "platform-entity|" + slotId); same value every time.
- Postgres stores implementing the existing admission interfaces (ActiveEntityCandidates, EntityGroupGrants,
  OidcConnectionBindingResolver; MachineEntityBindings through a small app-supplied interface), with one login
  connection per customer shared by its entities.
- ActivatedSlots for platform-licensing, read from idn_entity.
- Slot activation API for the apps (activate + name an entity; refuses slots not in the licence; never deletes; audited
  by the caller).
- RoleMappingFile accepts slot IDs (ENT-…) and a product code; MappingPlan gives add/remove per entity and product.
- Testkit with in-memory versions.
- Tests: tables only via the schema run, DML-only user runs everything, UUID derivation stable, one connection shared by
  two entities, grants separated by product code, activation rules, NOT_IN_LICENCE status, startup refusal codes.

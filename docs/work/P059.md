## B. Part 1 — field stores in the app's transaction (LV-25.2; note section 1)

## D. Part 3 — dropdown display names (LV-28)

In `platform-fields`, a `DROPDOWN` field's options become **a code plus an optional display name, in the order the admin sets**:
- The **code** stays the stored, matched and searched value: values, fingerprints, search, imports and the primary rule are unchanged.
- The **name** is for display only, and can be edited without touching stored values. An option without a name shows its code.
- Names are unique within a field, with the same length and character limits as field labels. They are configuration, not sensitive.
- **Existing definitions read as code-only**, in their stored order, so nothing in use breaks. If the order isn't kept today, keeping it is part of the fix.
- Public API: additive (for example an `Option` record `(code, name)` and `options()` returning them, with the existing code list kept). Any schema change is a new additive migration.
- Tests: the order is kept through save, read and change; names change without touching any stored value; a duplicate name is refused; an existing code-only definition reads unchanged; search and import still match by code.

## B. Build

### B1. Login connection: drafts, test sign-in, activate, rollback (platform-identity)

The table already allows `DRAFT`, `VALIDATED`, `ACTIVE`, `DISABLED`. Build the operations an app's IT Admin screen calls, in identity-core (store interface plus `LoginConnections` service) with Postgres and in-memory versions:

- **Draft:**
  - `createDraft` copies the ACTIVE connection, or creates the first one; `updateDraft` changes it. Both use an expected version.
  - At most one DRAFT or VALIDATED connection per customer and product.
- **Test sign-in:** `validate(draftId, TestSignIn)`.
  1. Fetch the issuer's discovery document and keys through the same safe outbound rules as integration (https only; the address guard).
  2. Check that the issuer matches.
  3. Optionally check a test token the admin pasted, or got through a test sign-in: signature, issuer, the audience the product expects, expiry, and the group claim present.

  The result has a specific cause per failure (`IDN_TEST_*` codes: issuer unreachable, discovery mismatch, keys missing, token signature, audience, expired, groups claim missing). A pass moves the draft to VALIDATED. A later edit moves it back to DRAFT.
- **Activate:** `activate(validatedId)` makes it ACTIVE and the old one DISABLED, in one transaction. Only a VALIDATED connection can be activated.
- **Rollback:** `rollback(customer, product)` reactivates the previous ACTIVE version from history, as a new version. It is refused when there is none.
- **Setup and the screen:** setup's existing "connection changed in the app since the last setup" conflict still works. `--replace-connection` replaces the ACTIVE connection; drafts are left alone.
- **History:** every step writes a history row with who, when and the source (APP or SETUP). The app audits as it does today.

### B2. http issuers for local test login servers only (setup and identity)

- An `http` issuer is allowed only when its host is `localhost`, `127.0.0.1` or `[::1]`, **and** the licence is signed by a development key (from `trusted-keys.json`).
- Otherwise it is refused: `SETUP_HTTP_ISSUER_NOT_ALLOWED` in setup, `IDN_HTTP_ISSUER_NOT_ALLOWED` in the connection operations.
- Every other rule is unchanged (no query; an `https` issuer as before).

### B3. Role aliases in `product-roles.json` (setup)

- **Format:** `platform-product-roles/1` gains an optional `"aliases": { "<identity role name>": "<role>" }`.
  - An alias may not equal a role or another alias, and its target must be a role.
  - Older files still load.
- **Use:** the role-mapping file may use an alias. It is resolved when the file is read and stored as the canonical role. The plan shows `alias → role`.
- Unknown names are refused as today.

### B4. Grant history `idn_grant_history` (identity schema V3)

- **New file:** `V3__grant_history.sql`. Do not edit V1 or V2. `IdentitySchema.VERSION = 3`.
- **Table:** insert-only, one row per entity per grant change, with:
  - customer, product, entity;
  - group (issuer and group name);
  - role before and role after (null for add or remove);
  - change (ADDED, REMOVED, CHANGED);
  - source (SETUP, APP);
  - who, when, and the setup run ID when the source is setup.

  Triggers refuse UPDATE and DELETE, even for the owner.
- **Writers:** setup writes the rows in its transaction, and `GroupGrantStore` changes made by an app write them too.
- **Reading:** `GrantHistory.forEntity(entity, from, to)` for the app's audit page. The DML-only runtime user is enough.

### B5. Customer-keys guard (setup)

- `product-roles.json` gains an optional `"customerKeys": "required" | "optional"`; a missing value means `optional`, which is today's behaviour.
- With `required`, `--no-customer-keys` is refused with `SETUP_CUSTOMER_KEYS_REQUIRED`, whatever the licence.
- Confirm in a test that a customer stored with `--no-customer-keys` gets both keys from the next run without the flag, and that nothing else changes.

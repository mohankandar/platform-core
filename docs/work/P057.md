# Task P057 — design note for platform-core 1.3.0 (LV-25.2 transactions, LV-24.3 outbound for OAuth and SMTP). Design only, no code.

Written 2026-11-25 by the Shared capabilities thread. Plan: board SH-36, agreed by LexaVault (LV-27) and Vero (SDV-51). Starts after P056 (1.2.0). Read CLAUDE.md, docs/work/README.md, the fields, notifications and outbound design docs, and the code they describe.

**Write `docs/design/1.3.0-transactions-and-outbound.md` and merge it by PR. Change no code.** The design chat reviews it, posts it on the board for both apps, and writes the build task after.

## What the note must settle

1. **LV-25.2: the field stores join the app's own database transaction** (`PostgresFieldStore`, `PostgresValueStore`), so an app can save its own row and the field values atomically.
   - How the app hands its transaction over (a `Connection` per call, a `DataSource` aware of Spring transactions, or a transaction callback), and which one works for an app with and without Spring. Prefer the one that changes no existing behaviour: today's self-managed transaction stays the default.
   - Locks, isolation and retries the stores rely on today (for example the conflict checks) and what changes when they run inside the app's transaction; what the app must not do.
   - Tests that would prove it (rollback of the app's transaction leaves no field values; the conflict check still holds).
2. **LV-24.3: Microsoft sign-in (OAuth) and SMTP through `platform-outbound`** (proxy, allow-list, time-outs). **Opt-in only** (LexaVault and Vero agreed): a setting that is off by default, so no installation loses mail on upgrade. What happens for SMTP (not HTTP) with the proxy and allow-list; what the install guide says; how the startup check reports a mail host missing from the allow-list once opted in.
3. For each: the public API it adds (exact signatures), the settings (names, defaults), any schema change (none expected), the risks, and a rough size of the build.

# platform-core

Shared platform libraries for document products. Each app pulls these modules in as **libraries** (released jars on
its classpath, from GitHub Packages). platform-core is not a server, has no `main`, and is never deployed on its own.

## Modules

| Module | What it is |
|---|---|
| `platform-bom` | Bill of materials. Lists every platform module at the platform version. Products import it in `dependencyManagement`. |
| `platform-identity-core` | Identity: claims, OIDC connection bindings, entity admission, role mapping (role aliases through `EntityRoleCatalog.aliasTarget`). Login-connection drafts for the IT Admin screen: `store.LoginConnections` (draft, test sign-in, activate, rollback, discard; `ConnectionOutcome` with `IDN_*` codes; one DRAFT or VALIDATED per customer and product); test sign-in `signin.OidcTestSignIn` (discovery + JWKS through an `IssuerFetch`, optional token: signature RS/PS/ES, issuer, audience, expiry, groups claim; `IDN_TEST_*` codes; the token never stored or shown); `signin.LocalTestIssuers` (http only on localhost / 127.0.0.1 / [::1] under a development-key licence, `signin.DevelopmentLicence`). Grant history: `GrantHistory`, `GrantChange`, `GrantAuthor`. No framework dependencies. |
| `platform-identity-spring` | Spring Security adapters for identity (JWT normalizer, audience validator, caching binding resolver). Auto-configuration (optional dependencies): `LoginConnections` on the identity JDBC store (`PostgresLoginConnectionStore` on the app's DataSource after `IdentitySchema.verify`), with `OutboundIssuerFetch` over platform-integration's `Outbound` bean when platform-integration-spring is there, and `DevelopmentLicence` from platform-licensing-spring's licence service (else `NONE`); every bean backs off for the app's own. |
| `platform-identity-jdbc` | Identity storage (plain Java, no Spring): `idn_` tables and SQL (`db/platform/identity`, history table `idn_schema_history`, run only by the app's schema step) with startup check `IdentitySchema.verify`; Postgres stores for customers, entity slots (`entity_uuid` derived from the slot ID by `EntityUuid`), login connections per customer and product with history (drafts, activate and rollback in one transaction; `idn_login_connection_one_pending`), group grants per product with their history (V3: `idn_grant_history`, insert only by triggers, written in the same transaction, `PostgresGrantHistory`); `LicenceSigningKey` (the licence in force signed by a development key); `PostgresIdentityLookup` (candidates, grants, binding resolver), `PostgresMachineEntityBindings` (built-in `PostgresMachineClients` over `idn_machine_binding`, V2: integration client bindings per customer, product and client ID, ACTIVE or INACTIVE, with history, store `PostgresMachineBindingStore`; or an app-supplied `MachineClients`), `LicenceSlots` for `SlotActivation` (activate, rename, suspend, resume; activation and resume follow the intake rule; a slot back in the licence gets its earlier status from `status_before_removal`); time zones per customer and entity (`idn_customer.time_zone`, `idn_entity.time_zone`, IANA names; `EntityTimeZones`: the entity's own zone, else the customer's; `TIME_ZONE_INVALID`). Store interfaces, `SlotActivation` and `EntityTimeZones` live in identity-core (`com.documentplatform.identity.store`). Install guide: `docs/install/identity.md`. |
| `platform-identity-testkit` | Test support for identity storage: `InMemoryIdentityStore` (all stores and lookups in memory, client bindings included, drafts, rollback and grant history included); `testkit.MockIssuer` (generic mock OIDC issuer on 127.0.0.1: discovery, JWKS, signed test tokens, failure switches; `startHttps(SSLContext)` for an https issuer named `localhost`). Test scope only. |
| `platform-notifications` | Notifications (plain Java, no Spring): event catalogue, admin settings, routing, summaries, continuous-condition alerts, message content rule, per-entity time zones (app supplies `EntityZones`) and the customer's zone from identity (`CustomerZones`; else the tenant's zone of the settings); outbox with retries; SMTP (password login or relay, or Microsoft 365 with OAuth 2.0 `AUTH XOAUTH2`: `MicrosoftOAuth`, `MicrosoftTokens`, client certificate or secret via `SecretResolver`), Teams (Workflows webhook) and Slack senders; approval links (`approval.Approvals`: Approve / Decline links in messages, signed single-recipient expiring `ActionTokens` (HMAC, key via `SecretResolver`), first decision wins in `notif_approval_request`, outcome to the requester, optional "expired" event to the requester (`ApprovalType.whenExpired`, `Approvals.tellExpired`); the app builds the page); Postgres stores and SQL migrations (`db/platform/notifications`). Design: `docs/design/notifications.md`. |
| `platform-notifications-testkit` | Test support for notifications: in-memory channel, recipient resolver, secret resolver and stores (approval store included). Test scope only; never in production code. |
| `platform-notifications-spring` | Spring Boot wiring for notifications: auto-configuration, `platform.notifications.*` properties (validated at startup; `mail.auth` PASSWORD or OAUTH2_MICROSOFT with `mail.oauth.*`), startup check of the `notif_` tables (never creates them), scheduled tick and background sender, the customer's time zone from identity when the app has `EntityTimeZones` as a bean, health indicator per destination and the mail sign-in mode and token state, approval links when `approvals.link-key-secret` is set (app supplies `ApprovalType` beans and an `ApprovalAudit`; the tick tells requesters of expired requests and purges requests expired longer than `retention` ago daily). Install guide: `docs/install/notifications.md`. |
| `platform-licensing` | Licensing (plain Java, no Spring, no runtime dependencies): Ed25519-signed licence file and verifier with refusal codes, trusted keys (`platform-licence-keys/1`, optional `"development": true` per key, `TrustedKeys.isDevelopmentKey`), licence states with 30-day grace, effective-time clock rule and signed last-seen reset, `LicenceService` (current + waiting licence), usage levels (never blocks), hash-chained usage ledger with chain head, usage file export and verifier, Postgres stores (plain JDBC) and SQL (`db/platform/licensing`), licence-issuing command (`IssueLicenceCommand`, our side only; signs in Vault Transit with `VaultTransitSigner`, the private key never leaves Vault; set-up: `docs/install/licence-signing.md`), notice log of published licensing notifications, licence command (`LicenceCommand`, customer side). Design: `docs/design/licensing.md`; formats: `docs/design/licensing-file-format.md`. |
| `platform-licensing-testkit` | Test support for licensing: in-memory licence store, usage ledger, last-seen store, notice log, signer, throwaway test keys and licences. Test scope only. |
| `platform-licensing-spring` | Spring Boot wiring for licensing: auto-configuration of `LicenceService`, `platform.licensing.*` properties (validated at startup; `tenant-id` required; keys from `trusted-keys-file` and/or inline `trusted-keys`), startup check of the `lic_` tables (never creates them) and of the stored licence, health indicator, licensing notifications (`LicensingEvents` for the app's catalogue, hourly check per activated entity slot, including "Licence does not cover this product") when the app has `platform-notifications` (optional dependency). Install guide: `docs/install/licensing.md`. |
| `platform-setup` | The setup command (plain Java, no Spring), direct sign-in mode: `SetupCommand` (`setup plan|apply`) reads the signed licence, the sign-in file (`platform-signin/1`), the role mapping CSV (slot IDs) and the product's `product-roles.json` (optional `aliases`, resolved when the mapping is read and stored as the role; optional `customerKeys` `required` or `optional`); preflight with `SETUP_*` codes, plan, then one transaction per product database under `pg_advisory_xact_lock` (licence, customer, slots, login connection, grants, integration client bindings from the optional `client-bindings-<product>.csv` named in the sign-in file with the product's `sources`: `ClientBindingsFile` in identity-core, `SETUP_CLIENT_BINDINGS_INVALID` with line numbers, a removed line switches the binding off; optional `integrationProfiles` (name, file, tag) per product, each checked with `ProfileValidator` in preflight, listed as `checked`, stored nowhere; `SETUP_PROFILE_INVALID`, `SETUP_PROFILE_TAG_MISSING`), tenant-id config fragment, run log; creates the customer's keys in the key service (`SetupKeys`, before the database part; existing keys left alone; `--no-customer-keys` skips, refused with `SETUP_CUSTOMER_KEYS_REQUIRED` when the product requires the keys); `http` issuer only on this machine under a development-key licence (`SETUP_HTTP_ISSUER_NOT_ALLOWED`); grant history rows with the run ID (`run=` in the run log); the app's login-connection drafts left alone; optional default time zones for the customer and per slot in the sign-in file (stored only where none is set). DB and key service (`PLATFORM_SETUP_VAULT_*`, set-up policy) settings from the environment only. Demo input files (development key) in `platform-setup/demo/`. Install guide: `docs/install/setup.md`; design: `docs/design/setup.md`. |
| `platform-fields` | Case field definitions and values (plain Java, no Spring; depends only on `platform-crypto`; package `com.documentplatform.fields`): `FieldSpec` per entity and product (`FieldScope`: entity UUID + product code) with types TEXT, NUMBER, DECIMAL, MONEY (one currency), DATE, DATE_TIME (with offset), EMAIL, UUID, DROPDOWN (≤100), ADDRESS (US parts with optional street2, country ready), CUSTOM_PATTERN, rules, flags (primary, searchable + `SearchMode`, sensitive (names and addresses by default; EXACT search only), multi-value, displayable), display order, active; `FieldValidator` / `FieldSet` (stable `ValueError` codes, messages never hold a value); `FieldDefinitions` (key never changes, type, sensitive and primary locked once the app's `FieldValuesCheck` says values exist, removing = switching off, history, app-only settings by key); field list file `file.FieldListFile` (`platform-fields/1`) with import by key (`ImportReport`: CREATE / UNCHANGED / CONFLICT); delivery `delivery.FieldDelivery` (`platform-field-values/1`: key + type + value(s)) and its verifier (`DELIVERY_*` codes); Postgres `jdbc.PostgresFieldStore`, SQL `db/platform/fields` (history table `fld_schema_history`, run only by the schema step), startup check `FieldSchema.verify`. Value storage `values.FieldValues` per app record (`RecordRef`: scope + record type + record ID): one record per primary value set per entity, product and record type (unique index on `fld_record.identity`, safe with concurrent writers; `claim` finds or makes the record, adds missing values, refuses different ones), sensitive values only sealed under one record envelope (`RecordCipher`) plus a fingerprint for exact search, search EXACT / PREFIX / PARTIAL (`pg_trgm` index, else prefix with a note), `read` (sensitive hidden) vs explicit `readSensitive` (one key service call), `erase` (only through the erase log: any caller but its `CaseFieldsEraseHandler` gets `VALUES_ERASE_OUTSIDE_LOG`; deletes the record, its envelope and values; app-supplied `LegalHolds`; not crypto-shredding of backups), `VALUES_*` codes; `jdbc.PostgresValueStore` (`fld_record`, `fld_value`; optional `db/platform/fields-optional/partial-search.sql`). Design: `docs/design/case-fields.md`; install guide: `docs/install/fields.md`. |
| `platform-fields-testkit` | Test support for case fields: `InMemoryFieldStore` and `InMemoryValueStore` (same rules as Postgres), `TestValuesCheck`. Test scope only. |
| `platform-crypto` | Encryption and keys (plain Java, no Spring, no runtime dependencies; package `com.documentplatform.crypto`): `KeyService` plug-in point (per-customer wrapping key and fingerprint key that never leave it; Vault Transit now, AWS KMS / Azure Key Vault later), `vault.VaultClient` (Transit and KV v2; `VaultAuth` token, token file or AppRole; no redirects), `vault.VaultKeyService` (keys `customer-<hex>` and `-fp`, created by the set-up step only), `envelope.ValueCipher` (AES-256-GCM per value, `pcv1.` text, bound to customer and context), `envelope.RecordCipher` (record envelope: all sensitive values of one record under one data key, `pck1.` envelope + `pci1.` items, one key service call per record), `envelope.StreamCipher` (64 KiB chunks, format `platform-stream`), key versions, rotation, rewrap, retired versions; `fingerprint.Fingerprinter` (HMAC-SHA256 in the key service, for exact-match search; batches in one call); customer key destruction at customer exit (`KeyService.destroyCustomerKeys`, `KeyDestruction`; command `command.CryptoCommand` `crypto destroy-customer-keys`: tenant ID typed back, login from `PLATFORM_SETUP_VAULT_*` via `vault.VaultEnvironment` with the set-up and `platform-crypto-offboard` policies (the set-up policy alone cannot delete), result `platform-key-destruction/1` for the offboarding certificate with two dates: live data destroyed on, unreadable everywhere incl. backups from (+ backup retention)); `CustomerId.fromTenantId` (name-based UUID of `TEN-…`); `CRYPTO_*` codes, no secret in any output. Design: `docs/design/crypto.md`. |
| `platform-crypto-testkit` | Test support for crypto: `InMemoryKeyService` (versions, rotation, retired versions, down / denied, call counter). Test scope only. |
| `platform-crypto-spring` | Spring Boot wiring for crypto: `platform.crypto.*` properties (validated at startup; Vault address, namespace, login APPROLE / TOKEN_FILE / TOKEN, Transit mount, key prefix, tenant ID defaulting to `platform.licensing.tenant-id`), `VaultClient` + `VaultKeyService` (backs off for an app-defined `KeyService`), `ValueCipher`, `RecordCipher`, `StreamCipher`, `Fingerprinter`, `CustomerId` beans; Vault never called at startup; health indicator `keyService` (state and `CRYPTO_*` code, no secrets). Install guide: `docs/install/crypto.md`. |
| `platform-erase-log` | Erase log (plain Java, no Spring; platform-fields optional; package `com.documentplatform.eraselog`), shared by the apps: one entry per erasure (`EraseRequest`: entity, product, record type + ID, app-defined kind such as `document` / `case-fields`, when, by rule or person, audit ID; never a value, `ERASE_ENTRY_VALUE_REFUSED`), numbered and SHA-256 chained (`EraseLog.verify`); kept **outside** the database it protects (`EraseLogStore`; built: `file.FileEraseLogStore`, append-only, fsync before acting, file lock for several instances; install rule in `docs/install/erase-log.md`); applied position in the app database (`jdbc.PostgresErasePosition`, `erl_position`, SQL `db/platform/erase-log`, history table `erl_schema_history`, run only by the schema step, check `EraseLogSchema.verify`; DML-only user; never moves back); `Eraser` (handler check, log durably, erase, advance; pending entries caught up); `EraseGuard` (restored database → `ERASE_LOG_RESTORE_DETECTED`, no work until replay; also wrong log, gap, chain broken, unreachable); `EraseReplay` (handlers per kind, safe twice, stops with the handler code, verify step, then the guard lifts); `EraseRetention` (backup 30–90 days, default 35, log keeps +30, pruning from a checkpoint); built-in `fields.CaseFieldsEraseHandler`. Design: `docs/design/erase-log.md`. |
| `platform-erase-log-testkit` | Test support for the erase log: `InMemoryEraseLogStore` (tampering, down), `InMemoryErasePosition` (snapshot / restore), `RecordingEraseHandler`. Test scope only. |
| `platform-erase-log-spring` | Spring Boot wiring for the erase log: `platform.erase-log.*` (location required, `backup-retention-days` 30–90, `recheck`, `exit-after-replay`), file store, Postgres position on the app DataSource after the startup check (never creates tables), the app's `EraseHandler` beans, `Eraser`, `EraseGuard` checked at startup (a restore starts the app blocked, OUT_OF_SERVICE), `EraseLogWorker` (recheck, daily chain check and pruning), `EraseReplayRunner` (`--erase-replay`), health `eraseLog`. New capability = new module, added to the root `<modules>` list **and** to `platform-bom`.

## One version

Every module inherits its version from the root `pom.xml`. Never set a `<version>` in a module POM other than
in its `<parent>` block. Inter-module dependencies use `${project.version}`. A release bumps all modules together.

## Build

```
mvn verify      # compile + all tests (the only local check; no `mvn install` into the shared ~/.m2)
```

Apps use **released versions only**, from GitHub Packages (`https://maven.pkg.github.com/mohankandar/platform-core`).
A release is a tag `platform-core-vX.Y.Z` on main; the release workflow publishes it. Tags are never moved or reused.
For an offline build of a tag into a separate local repository: `scripts/build-release.ps1` / `scripts/build-release.sh`.
Merges into main go through pull requests with green CI (`.github/workflows/ci.yml`); see `docs/work/README.md`.

Java 21, Maven 3.9+.

On the owner's Windows laptop, Norton 360 intercepts TLS; Maven trusts it via the user environment variable
`MAVEN_OPTS=-Djavax.net.ssl.trustStoreType=Windows-ROOT`. Never add machine-specific settings to the repo.

## Rules

- **Independence.** platform-core never names, depends on or assumes any product. Product-specific behaviour is
  profile **data** published by the API's owner (format `platform-integration-profile/1`), never code or files here.
  Tests use made-up profiles only. Apps plug their specifics in through interfaces (for example `EntityRoleCatalog`)
  and configuration. `NoProductNamesGuardTest` fails the build on a product's name in code, SQL, JSON, XML, YAML,
  properties, CLAUDE.md, README files or `docs/install/`.
- **Released versions only across repos,** from GitHub Packages; tags are never moved.
- **Merges go through pull requests with green CI.**
- **Never log secrets, document content or redacted values.** That includes tokens, client secrets, keys,
  passwords, raw claims, file contents, and anything that was redacted. Log ids and neutral reasons only.
- Keep Java package names stable; renames are their own task.
- **Coordinates and packages.** Every module uses groupId `com.documentplatform.platform`. A new module puts its
  code in `com.documentplatform.<capability>` (for example `com.documentplatform.notifications`). The identity
  modules keep their existing `com.documentplatform.identity...` packages.
